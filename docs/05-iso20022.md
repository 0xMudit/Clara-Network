# 5. ISO 20022 — Payments Messaging (Clearing & Settlement)

## 5.1 What ISO 20022 is

**ISO 20022** is the international standard for financial messaging, defining
a common repository of business models, message definitions, and **XML**
(and now JSON) schemas. It is replacing legacy SWIFT **MT** formats and national
formats across payments, securities, trade, and cards. It is the standard for
**interbank clearing and settlement** messages (e.g. SWIFT CBPR+, TARGET2,
SEPA, RTGS/RTP systems worldwide).

Namespaces look like:
`urn:iso:std:iso:20022:tech:xsd:pacs.008.001.09`.

## 5.2 Message categories (business areas)

~700 message definitions in 16 categories. The payment-relevant ones:

| Prefix | Area | Examples |
|--------|------|----------|
| `pain` | **Payments Initiation** (customer to bank) | pain.001 credit transfer initiation, pain.008 direct debit initiation, pain.013 request for payment |
| `pacs` | **Payments Clearing & Settlement** (bank to bank) | pacs.008 customer credit transfer, pacs.009 FI credit transfer, pacs.002 status report, pacs.004 return, pacs.028 status request |
| `camt` | **Cash Management / Account reporting** | camt.052 account report, camt.053 statement, camt.054 debit/credit notification, camt.056 cancellation request, camt.029 cancellation response, camt.110/111 investigations |
| `reda` | Reference data | |
| `acmt` | Account management | |
| `semt`/`seev`/`sese` | Securities | |
| `tsmt`/`tres` | Trade services / treasury | |

## 5.4 Key concepts

- **XML schema per version**: e.g. `pacs.008.001.09` (v9) is the CBPR+ version;
  SEPA uses `pacs.008.001.02`. Card-scheme-relevant usage guidance exists from
  Visa/Mastercard for ISO 20022 conversion of card clearing data.
- **UETR** (Universally Unique End-to-end Transaction Reference, UUID) is a
  mandatory element in CBPR+ for tracing a payment end-to-end.
- **Structured addresses**: SEPA 2025 rulebook phases out unstructured address
  format (from 15 November 2026 the unstructured address can no longer be
  provided in EPC payment messages).
- **Harmonisation**: BIS CPMI + PMPG harmonised data models for cross-border
  payments (credit transfers pacs.008/009/002, returns camt.056/camt.029/
  pacs.004, investigations pacs.028/camt.110/camt.111). Remittance info up to
  140 chars unstructured or 9,000 chars structured (excluding XML tags).

## 5.5 Typical bank-to-bank credit transfer flow (pacs.008)

```
Debtor (customer)
   │ pain.001
   ▼
Debtor Agent (instructing FI)
   │ pacs.008
   ▼
[ Intermediary agent(s) ] ──┐
   ▼                        │ camt.052/053/054 reporting to each FI
Creditor Agent (instructed FI)
   │
   ▼
Creditor (customer)
```

Parties in ISO 20022 (vs MT):

| MT | ISO 20022 |
|----|-----------|
| Ordering Customer (50F) | Debtor (`Dbtr`) |
| Ordering Institution (52) | Debtor Agent (`DbtrAgt`) |
| Intermediary (56) | Intermediary Agent (`IntrmyAgt`) |
| Account with Institution (57) | Creditor Agent (`CdtrAgt`) |
| Beneficiary (59) | Creditor (`Cdtr`) |
| Sender | Instructing Agent |
| Receiver | Instructed Agent |
| Ultimate ordering customer | Ultimate Debtor (`UltmtDbtr`) |
| Ultimate beneficiary | Ultimate Creditor (`UltmtCdtr`) |

pacs.008 main elements (harmonised model): GroupHeader (msg id, creation time,
instructing/instructed agents, settlement info), PaymentInstruction / Credit
Transfer Transaction Information with PaymentId (InstrId, EndToEndId, TxId,
UETR), PaymentTypeInformation (priority, clearing channel, service level,
local instrument, category purpose), InterbankSettlementAmount, ChargeBearer,
Debtor/DebtorAgent/CreditorAgent/Creditor + accounts, RemittanceInformation,
and SupplementaryData.

## 5.6 ISO 20022 vs ISO 8583

| | ISO 8583 | ISO 20022 |
|--|----------|-----------|
| Scope | Card-originated messages (auth/clearing) at the switch | Interbank payments & reporting (RTGS, SEPA, SWIFT) |
| Format | Binary/ASCII bitmaps + fixed/variable fields | XML (or JSON) structured business messages |
| Versioning | Editions 1987/1993/2003/2023 | Namespaced versions per message (e.g. .001.09) |
| Used by | Card schemes, switches, acquirers/issuers for card txns | Banks, clearing houses, RTGS/RTP, PSP settlement |
| Example | `0100` auth request | pacs.008 credit transfer |

Visa (VisaNet Connect) and modern card platforms increasingly expose
card-transaction messaging **as ISO 20022-style REST APIs** (JSON), using
conventions aligned to ATICA/ISO 20022 names, while the wire between members
remains ISO 8583-based. Mastercard's **IPM** clearing and Visa's **BASE II**
remain ISO 8583-flavored on the card rails.

## 5.7 Design guidance

- If you build a **card scheme/switch**, ISO 8583 is your protocol (see
  `04-iso8583.md`). ISO 20022 is what you will speak **when settling with
  central banks / RTGS** and for merchant/correspondent payouts.
- If you build a **PSP/gateway**, ISO 20022 (pain/pacs/camt) matters for
  payouts, direct debits, reconciliation, and bank integrations.
- Use **strict XSD validation** per message version, and maintain a
  **version registry** (many producers run multiple versions in parallel during
  migration).
- Keep **UETR** and **EndToEndId** stable end-to-end for reconciliation.
- Plan a **mapping layer** between internal canonical models and pain/pacs/camt
  for both outbound and inbound.

## Problem Statement

The Clara Network admin dashboard has three problems:

1. **The throughput error** — "Couldn't load data: The Admin API is temporarily unavailable." The BFF proxy calls `tryFetchAdmin("/dashboard/series")` which fails because the Go admin API isn't reachable from Vercel. Every ops page visitor sees a broken chart.

2. **The login flow is generic** — A plain role picker on a white background. No marketing value. Visitors see a list of roles and nothing else. No reason to be excited.

3. **The ops page is buried** — The best page (network throughput, transactions, clearing stats) is only visible after login. The public sees a login form instead of the product.

## What Makes This Cool

The landing page IS the product showcase. Visitors see the real Clara dashboard (with mock data) before they log in — live-feeling transaction charts, settlement stats, network activity. The role picker is the CTA, not a separate page. Click a role → you're in. The "whoa" moment is: "wait, this is the actual product?"

## Constraints

- Next.js 16 app with shadcn/ui, Tailwind v4, recharts
- Dark mode by default (matches financial tools: Stripe Dashboard, Vercel, GitHub)
- Mobile responsive — works on phones, not just desktop
- Must keep the existing role-based routing structure (scheme_operator → /ops, issuer → /issuer, etc.)
- The Go admin API is not reachable from Vercel — mock data layer needed
- GitHub link must be visible on the landing page

## Premises

1. **The role-based app structure is sound** — we're upgrading the entry point and visual polish, not rebuilding the backend. Agree/disagree?
2. **Dark mode by default** is the right call for a financial/infrastructure tool (Stripe, Vercel, GitHub all default dark). Agree/disagree?
3. **Mock data needs to feel real** — fake but plausible payment data. Not "Lorem ipsum" style. Real-looking STANs, amounts, response codes. Agree/disagree?
4. **Mobile responsive is core, not bolt-on** — must work as well on phones as desktop. Agree/disagree?
5. **The landing page + login are ONE page** — not two separate pages. Agree/disagree?

## Approaches Considered

### Approach A: Single Immersive Page
Hero + role cards on one page. No marketing section. Minimal, fast, clean.

- Effort: M
- Risk: Low
- Rejected because: No room for the "Stripe-like showcase" feel. Too sparse.

### Approach B: Stripe Double-Panel (CHOSEN)
Full-width marketing hero with gradient background + GitHub link + feature pills. Below: role selection cards with one-click sign-in. The hero sells, the cards convert.

- Effort: M-L
- Risk: Low
- Chosen because: Matches the stated goal (Stripe-like showcase, landing + login mix, addictive UX). Most visually impressive. Feature pills provide social proof. GitHub link is natural.

### Approach C: Dashboard Preview + Auth
Landing page shows a live mock dashboard. Most ambitious, most engaging.

- Effort: L
- Risk: Med
- Rejected because: Mock data layer complexity is substantial and better spent on fixing all dashboard pages, not just the landing page.

## Recommended Approach

**Approach B: Stripe Double-Panel**

### Page structure

The landing page (`src/app/page.tsx`) is a server component that checks `supabase.auth.getUser()` — if logged in, redirect to `HOME_BY_ROLE[role]` (same as current behavior). The landing page only renders for unauthenticated visitors.

1. **Hero section** (full viewport height on desktop, compact on mobile)
   - Full-width gradient background (dark indigo/violet via oklch, matching the login hero's gradient)
   - Decorative orbs (CSS-only, no JS animation — two blurred circles with violet/sky tints)
   - Grid pattern overlay at 3% opacity for texture
   - "Clara Network" logo + tagline: "The payment network you build yourself."
   - Subtitle: "Open-source Mastercard / Visa-style card switching, clearing, settlement, and issuing"
   - Feature pills: "ISO 8583 + 20022", "Real-time auth", "Self-hosted"
   - CTA: "Try the Demo →" scrolls down to role cards (anchor link)
   - GitHub link in the top-right nav + bottom attribution
   - **Mobile (< lg):** compact hero at ~40vh — logo + tagline + CTA button, no full gradient panel. Role cards appear immediately below. Matches the current login behavior of hiding the large hero on small screens.
   - **Desktop (lg+):** full-viewport hero with gradient, orbs, grid overlay, feature pills. Role cards below the fold.

2. **Role selection section** (below the fold, id="roles")
   - Section title: "Pick a role. Sign in instantly."
   - Role cards in a responsive grid (1 col mobile, 2 cols sm, 3 cols lg)
   - Each card: icon, role name, one-line description, arrow indicator
   - Color mapping per role:
     - scheme_operator → violet-500
     - issuer → sky-500
     - acquirer → emerald-500
     - merchant → amber-500
     - viewer → rose-500
   - **Click flow (3 steps):**
     1. User clicks a role card
     2. Client calls `supabase.auth.signInWithPassword({ email, password: "ClaraDemo!2026" })` using the same demo auth as the current login form
     3. On success, `router.push(HOME_BY_ROLE[role])` + `router.refresh()`
   - The landing page reuses the existing `LoginForm` component's `signInAs` logic — same Supabase auth, same demo passwords, same role routing
   - No separate /login page needed — this IS the login

3. **Footer**
   - "Open source · Built for county & bank engineers"
   - GitHub link
   - "Clara Network · Open-source payment infrastructure"

### Mock data layer

Create `src/lib/mock-data.ts` that provides realistic mock responses for the 3 endpoints the ops page and landing showcase use:
- `/dashboard` → `{ transactions: 1247, clearingRecords: 892, merchants: 156 }`
- `/dashboard/series` → 14 days of realistic transaction counts (varying 80-200/day)
- `/transactions?limit=6` → 6 recent auth transactions with realistic STANs, PANs, amounts, response codes

Other dashboard pages (clearing, settlement, ledger, cards, tokens, merchants, funding, disputes) are NOT mocked in this phase — they show the existing `DataError` state when the API is unavailable. Mock data is scoped to the landing page showcase and the ops page only.

Mock response code distribution: `["00", "00", "00", "00", "51", "14", "55"]` — weighted toward approval (00) with occasional declines (51 = insufficient funds, 14 = invalid card, 55 = incorrect PIN).

**Fallback behavior:** Mock fallback applies only to network errors and 5xx responses. 401/403 continue to return the existing access-denied messages ("You don't have access to this data.") — a real 401 means the session expired, and returning mock data would mask that.

### Dark mode default

Change the ThemeProvider to default to dark. The theme toggle remains for users who prefer light. Persist the user's theme preference in localStorage (next-themes already does this). Default is dark only for first-time visitors; returning users get whatever they last picked.

## GSTACK REVIEW REPORT

**Scope:** `feat/web-ui` · 16 files changed (6 new) · reviewer: auto (plan-eng-review + outside voice) · date: 2026-09-04

### Section 1 — Architecture (PASS with P1 fix)

- **P1 (fixed):** `supabase/middleware.ts` redirected ALL unauthenticated requests — including `/` — to `/login?next=…`, which would have made the public landing unreachable. Middleware now exempts `/` and `/login`. `/login` preserves `?next=` when forwarding to `/` so deep-link post-auth routing still lands where the visitor was headed. The BFF data route (`/api/data/…`) still independently authenticates, so exempting `/` does NOT leak admin data.
- Decision: mock fallback lives in `tryFetchAdmin` and covers only network errors and 5xx (500/502). 401/403 remain hard access-denied (a real 401/403 is a security/role signal, never masked).
- Decision: mock dates are generated **relative to `new Date()`** so the 14-day throughput window always looks live on the landing + ops pages.
- No security regression: demo auth is unchanged; the existing `DEMO_PASSWORD` is deliberately a well-known demo credential.

### Section 2 — Code Quality (PASS)

- **Single source of truth for demo credentials:** created `src/lib/demo-auth.ts` exporting `DEMO_PASSWORD`, `DEMO_EMAILS`, `ROLE_CARDS` (with per-role visual metadata + live demo stat), and the shared `signInAs(role, router, next?)` (honors safe same-origin `?next=`, falls back to `HOME_BY_ROLE`).
- Removed the duplicated `DEMO_PASSWORD` in the old `login-form.tsx`, which is now deleted (its function is fully covered by the landing role picker; `/login` merely forwards to `/`).
- **Surfaces:** `/` = hero + role cards (single sign-in). `/login` = redirect shim (kept for backward-compatible bookmarks plus `?next=`). Logged-in users hitting `/` or `/login` go straight to their dashboard.
- `console.warn` on the mock fallback is a server-only, three-lines-per-load diagnostic — accepted.
- The open-source "social network" placeholder copy in the first hero draft was corrected to proper payment-network copy.

### Section 3 — Tests (PASS — framework added)

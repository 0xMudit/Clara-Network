# 4. ISO 8583 — Financial-Transaction-Card-Originated Interchange Messages

## 4.1 What ISO 8583 is

**ISO 8583** is the international standard for **financial-transaction
card-originated messages** exchanged between **acquirers** and **card
issuers** (through the scheme/switch). It is the "language of card
switching" — the wire protocol used inside VisaNet, Mastercard, national
switches (e.g. NPS MIR), and most ATM/POS networks.

Versions: ISO 8583:1987, :1993, :2003, and **ISO 8583:2023** (current; third
edition). Visa and Mastercard each layer proprietary variants on top
(**VIS**/Visa formats, **MIP**/IPM for Mastercard), but they share the ISO 8583
message skeleton.

## 4.2 Message structure

Every ISO 8583 message has:

```
┌──────────────┬──────────────┬───────────────┬─────────────────┐
│ Message Type │  Primary     │  Secondary    │  Data Elements  │
│ Identifier   │  Bitmap      │  Bitmap       │  (fields)       │
│ (4 digits)   │  (8 bytes)   │  (8 bytes opt)│                 │
└──────────────┴──────────────┴───────────────┴─────────────────┘
```

1. **Message Type Identifier (MTI)** — 4 digits `XXY Z`:
   - 1st digit: **Message class**
     - `1` Authorization
     - `2` Financial presentment
     - `3` File action
     - `4` Reversal/chargeback
     - `5` Reconciliation
     - `6` Administrative/management
     - `8` Network management
   - 2nd digit: **Message function**
     - `0` Request
     - `1` Request response
     - `2` Advice
     - `3` Advice response
     - `4` Notification
     - `5` Notification acknowledgement
     - `6` Instruction
     - `7` Instruction acknowledgement
   - 3rd digit: **Transaction originator** — e.g. `0` acquirer, `1` issuer,
     `2` cardholder, `3` terminal, `6` card acceptor.
   - Examples: `0100` = authorization request; `0110` = authorization response;
     `0200` = financial presentment (purchase with capture) request; `0400`
     = reversal; `0420` = reversal advice; `0500` = reconciliation request.

2. **Bitmap(s)** — the bitmap indicates which data elements are present. Each
   **bit** in the 64/128-bit bitmap maps to a data element number. The primary
   bitmap (bits 1–64) is mandatory; bit 1 set means a secondary bitmap (bits
   65–128) follows; bit 65 set means a tertiary bitmap (bits 129–192).

3. **Data elements (DE)** — the fields, each with a defined format.

## 4.3 Data element formats

| Abbrev | Meaning |
|--------|---------|
| `n` | Numeric only |
| `a` | Alpha (incl. blanks) |
| `s` | Special characters only |
| `an` | Alphanumeric |
| `ans` | Alphanumeric + special |
| `b` | Binary |
| `z` | Track 2/3 code set (ISO/IEC 7813, 4909) |
| `..`, `...` | Variable length (indicator digits) |
| `x`, `xx` | Fixed length / max length |

Length types:
- **Fixed** — e.g. `n 4`.
- **LLVAR** (`..xx`, max < 100) — 2 leading digits give field length.
- **LLLVAR** (`...xxx`, max < 1000) — 3 leading digits give field length.

Representation: many schemes use **packed/BCD** numeric fields (e.g. STAN in
BCD), or ASCII. Worldpay's reference implementation, for example, uses
compressed (packed-unsigned) numeric fields.

## 4.5 Processing codes (DE 3)

Format `PP A1 A2`:
- `PP` = transaction type: `00` purchase, `01` withdrawal/cash advance,
  `20` return/refund, `30` cash disbursement, etc.
- `A1` = **from** account type: `00` default, `10` savings, `20` checking/DDA,
  `30` credit line, `40` universal.
- `A2` = **to** account type: same set.

Examples: `000000` = purchase, savings to savings; `203000` = refund from
credit to default.

## 4.7 ISO 8583:2023 highlights

- Normalized data types and updated **Annex C** data element definitions.
- **Annex E** message class definitions (with per-class mandatory/conditional
  element tables and condition codes `M`, `ME`, `00`–`49`).
- **Annex F** message and transaction matching rules.
- **Annex G/H** batch and file transfer examples.
- **Annex I** data transparency.
- Free access to the standards-maintenance-portal files at
  `standards.iso.org/iso/8583/ed-3/en/` and the X9.org ISO 8583 Maintenance
  Agreement pages (references and terms, annexes B–J, code tables).

## 4.8 Building an ISO 8583 switch — engineering checklist

- **Parser/serializer** for binary (packed BCD) and ASCII variants, fixed and
  LL/LLL variable fields, 64/128-bit bitmaps.
- **MTI dispatch** by class/function; state machine per transaction keyed by
  `STAN + transmission datetime + acquiring ID` (the "original data elements"
  tuple) so **reversals and chargebacks** match the original auth.
- **Idempotency**: dedupe on STAN/datetime; never process the same STAN twice.
- **BIN routing table** for issuer lookup; **network routing** (retry, fallback).
- **Screens** (validation rules) per message type: field presence, formats,
  amount consistency, currency codes, MCC validity, expiry, Luhn.
- **HSM integration** for MAC (DE 64/128) verification/computation (CBC-MAC),
  PIN block verification (ANSI X9.8 / ISO 9564), and CVV/iCVV checks.
- **EMV data passthrough** (DE 55) and cryptogram verification with the issuer
  or HSM (see `06-emv-chip.md`).
- **Logging/archival** of raw messages for audit and dispute handling.
- **Testing**: replay captures of real network traffic; test host simulators;
  performance test for peak TPS.

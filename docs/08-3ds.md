# 8. 3-D Secure (EMV 3DS)

## 8.1 What EMV 3DS is

**EMV 3-D Secure (3DS)** is the EMVCo protocol for **authenticating cardholders
in card-not-present (CNP) transactions** — e-commerce, in-app, and card-on-file.
It is the successor to legacy 3-D Secure 1.0 ("Verified by Visa", "Mastercard
SecureCode", "Amex SafeKey").

> "EMV 3DS is an e-commerce fraud prevention protocol that enables consumer
> authentication for CNP purchases, without adding unnecessary friction." — EMVCo

Purpose: enable the **issuer** to verify the person making an online purchase is
the legitimate cardholder; reduce CNP fraud; and in the EU, support **Strong
Customer Authentication (SCA)** under PSD2 (two-factor authentication). EMVCo
recommends **v2.2+** for optimum SCA functionality.

## 8.2 Actors

| Actor | Role |
|-------|------|
| **Cardholder** | The consumer in the browser/app |
| **3DS Requestor** | The merchant/app making the payment |
| **3DS Server** | The 3DS Requestor's/merchant's software that orchestrates 3DS on its side |
| **Directory Server (DS)** | The card network service that routes authentication messages between the 3DS Server and the ACS |
| **ACS (Access Control Server)** | Issuer-side system that evaluates risk and performs authentication (frictionless or challenge) |

## 8.3 The two flows

### 8.3.1 Frictionless flow (majority of transactions)

```
3DS Requestor collects device/browser data
   │ AReq (authentication request)
   ▼
3DS Server ──▶ DS ──▶ ACS (issuer)
   │                  │ risk-based decision: enough data?
   │                  ▼
   │              ARes: transStatus = Y (authenticated, frictionless)
   │ ◀────────────────┘
   ▼
3DS Requestor continues to authorization with 3DS results (ECI, CAVV/AAV, XID)
```

- Issuer accepts without challenging the cardholder.
- **Liability shift** applies even for frictionless.

### 8.3.2 Challenge flow (higher risk / SCA-required)

```
AReq ──▶ ACS ──▶ ARes: transStatus = C (challenge required)
   │                    + acsURL / challenge data
   ▼
3DS Requestor opens challenge window (browser iframe/full page, or in-app SDK)
   │ CReq (challenge request)
   ▼
ACS ── cardholder authenticates (OTP, biometrics, banking-app push, WebAuthn/FIDO)
   │ CRes (challenge response, transStatus = Y/N)
   ▼
3DS Requestor notifies and continues to authorization
```

- Challenge methods: one-time passcode, knowledge-based questions, biometrics,
  out-of-band (OOB) via mobile banking app, WebAuthn/SPC, **decoupled
  authentication** (auth happens outside the transaction flow, e.g. for MOTO
  and subscriptions).
- The challenge must begin within ~30s of the ARes and each interaction has a
  10-minute timeout.

## 8.4 Messages (protocol)

- **AReq / ARes** — Authentication Request/Response: transaction amount,
  currency, channel, device/browser data, card data, prior auth info, decoupled
  and challenge indicators, `threeDSRequestorAuthenticationInd`, message
  extensions.
- **CReq / CRes** — Challenge Request/Response: `threeDSSessionData`, `cres`.
- **RReq / RRes** — Results Request/Response (3DS Server ↔ DS, used when 3DS
  Server must fetch the final result).
- **PReq/PRes** — Payer messages (3RI, requestor-initiated).

Key fields in responses: `transStatus` (`Y` authenticated, `N` not
authenticated, `C` challenge, `U` unable, `A` attempted, `R` rejected),
`authenticationValue` (CAVV/AAV), `eci` (Electronic Commerce Indicator),
`dsTransID`, `acsTransID`, `sdkTransID`, `acsURL`.

- **ECI** tells the issuer how the transaction was authenticated (e.g. 05
  fully authenticated, 07 attempted, 06/01 not authenticated).
- **CAVV/AAV** (Cardholder Authentication Verification Value / Accountholder
  Authentication Value) proves authentication to the issuer during
  authorization.
- **3RI (3DS Requestor Initiated)** — merchant-initiated authentication without
  the cardholder present (recurring/subscription, add-card).

## 8.5 Channels / integration

1. **Browser-based (3DS Method + Challenge window)** — JS SDK in the checkout
   page; challenge rendered in an iframe/modal on the merchant site.
2. **App-based** — 3DS SDK embedded in the merchant's mobile app; in-app
   challenge; supports **OOB** authentication (fingerprint in banking app).
3. **3RI** — server-to-server, no UI.

**3DS Method**: an async step where the merchant's 3DS Server contacts the ACS
URL to collect browser data before AReq (improves frictionless outcomes).

**Message extensions** (EMVCo-defined): Device Acknowledgement, Bridging,
Attribute Verification, Travel Industry, Payment Token — extensible per
industry/regulatory needs.

## 8.6 Integration into the payment flow

1. Collect device/browser data (device fingerprint).
2. Submit AReq.
3. Handle ARes:
   - `Y` → frictionless, proceed to authorization with 3DS data.
   - `C` → render challenge, get CRes, proceed.
   - `N`/`R`/`U` → decide policy (decline, fallback, attempt).
4. Authorization: include `eci`, `authenticationValue/CAVV`, `dsTransID`/XID
   and the 3DS results in the ISO 8583 message (DE 48/55 subfields).
5. Issuer validates CAVV at authorization and applies liability shift.

## 8.7 Risk-based authentication & SCA exemptions

- Issuers use the rich AReq data (10× more than 3DS 1.0) for **risk-based
  analysis**; many transactions pass frictionless.
- Under PSD2, **exemptions** exist (low-value TRA, trusted beneficiaries,
  recurring/CoF, corporate cards, transaction risk analysis); the PSP can
  request exemptions via 3DS but loses **liability shift** if exempted.

## 8.8 Building a 3DS stack

**If you are an issuer:**
- Stand up an **ACS**: risk engine, challenge UI (browser templates per EMVCo
  requirements), OOB/OBI app integration, decoupled auth support.
- Validate CAVV and ECI at authorization; manage SCA compliance.

**If you are a merchant/PSP:**
- Integrate a 3DS Server (in-house or via a vendor like Cardinal, Stripe) and
  SDK for browser/app.
- Store `transStatus`, `eci`, `authenticationValue`, and `dsTransID` for
  reconciliation and dispute defense.
- Handle **falls back to 3DS 1.0** where 2.x isn't supported (rare today).
- Ensure 3DS runs **before** the authorization call.
